# M5.1 Benchmark & Cost Model: Item-Generation Strategy for AI Study Plans

**Scope note:** No file in this repo is literally named "M5.1"; the closest artifact is the
StudyCoach / StudyPlan generation pipeline (`src/core/domain/services/StudyService.ts`,
`src/pages/StudyCoach.tsx`, `src/components/study-coach/*`). This report treats "M5.1" as that
milestone — the design decision of **when and how AI-generated learning content (study plans,
flashcards/tasks, adaptive scheduling state) gets created, cached, and refreshed** — and
benchmarks it against how established learning/AI products separate these concerns. All product
claims are sourced from public docs/blogs; anything not directly documented is flagged **[inference]**.

---

## 1. How leading products separate knowledge, artifacts, caches, and adaptive state

| Product | Durable user knowledge (source of truth) | Generated artifacts | Cache | Adaptive/scheduling state |
|---|---|---|---|---|
| **Anki** | User-authored note fields + note type templates, stored in a local SQLite `collection.anki2` file ([Anki manual, "Files"](https://docs.ankiweb.net/files.html)) | Rendered card HTML is templated at review-time from note fields (Anki does not "generate" content — cards are a deterministic function of note+template), so there is effectively no separate artifact cache; cards are rows derived from notes | Media files cached in `collection.media`; review history cached in `revlog` table | SM-2 / FSRS scheduling parameters per card (`due`, `ivl`, `factor`, `reps`) stored in the same SQLite DB — state is small (a few ints/floats per card) ([FSRS spec](https://github.com/open-spaced-repetition/fsrs4anki/wiki)) |
| **Quizlet** | User- or teacher-authored term/definition sets ("Sets"), stored server-side | Auto-generated practice modes (Learn, Match, Test) are computed *on demand* from the underlying set — Quizlet's help docs describe these as study *modes* over one shared set of terms, not separately stored content ([Quizlet Help Center](https://quizlet.com/help)) | Q-Chat / AI features (Quizlet acquired by education-AI focus) cache AI explanations per term/session, but the canonical term list is never overwritten by AI output | Per-user, per-term mastery/progress tracked via their spaced-repetition-like "Learn" algorithm; state is a mastery score per (user, term) pair, decoupled from the set content itself |
| **Duolingo** | Course graph / curriculum authored by Duolingo (skills, lexemes) — this is centrally authored, not user-generated | Exercises are **algorithmically assembled at request time** from a bank of exercise templates + the lexeme/skill graph, not bespoke-generated per user via LLM for most content; Duolingo's engineering blog describes a "Birdbrain" model that predicts per-user, per-skill strength and picks/orders exercises accordingly rather than generating new exercise text per user ([Duolingo Engineering: "How we learn how you learn"](https://blog.duolingo.com/how-we-learn-how-you-learn/), ["Birdbrain"](https://blog.duolingo.com/birdbrain/)) | Exercise pool is precomputed/authored once and reused across millions of users — this is the core lever that keeps their marginal cost near zero; the "cache" is effectively the entire exercise bank | Per-user skill-strength / half-life regression (HLR) model — a small vector of decay parameters per user per skill, updated continuously from practice events ([Duolingo HLR paper, Settles & Meeder 2016](https://research.duolingo.com/papers/settles.acl16.pdf)) |
| **NotebookLM** | User-uploaded source documents (PDFs, docs, links) — Google explicitly grounds all outputs in these sources and does not train on them ([NotebookLM privacy FAQ](https://support.google.com/notebooklm/answer/14275965)) | Summaries, "Audio Overviews," study guides, FAQs are **generated on-demand per notebook** and are described in Google's documentation as being generated when requested rather than eagerly for every possible query; Audio Overviews explicitly render a file server-side and let you download/cache it | Generated artifacts (audio files, summaries) are persisted per notebook so the user doesn't pay generation cost again, but they are derived/regenerable, not authoritative | No public spaced-repetition/adaptive state — NotebookLM is a retrieval/generation tool, not a mastery-tracking tool |
| **ChatGPT Projects / Custom GPTs** | Uploaded project files + conversation history are stored as durable context; OpenAI's docs describe Projects as a container for files + chats, with retrieval (RAG) over files rather than injecting whole files into every prompt ([OpenAI Help: "What is a Project"](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)) | Each chat response is generated fresh per turn (no artifact caching of "the answer" beyond conversation history); file embeddings for retrieval are computed once and cached (index build), reused across many queries | Vector index / embeddings cache per uploaded file; prompt-level caching (OpenAI's `prompt caching` for repeated prefixes) reduces inference cost for repeated system/context prefixes ([OpenAI prompt caching docs](https://platform.openai.com/docs/guides/prompt-caching)) | Memory feature stores durable user facts across chats; this is a distinct, small, explicitly-editable store, separate from file embeddings and separate from generated answers ([OpenAI Memory FAQ](https://help.openai.com/en/articles/8983136-memory-faq)) |

### Cross-cutting pattern **[synthesis, supported by above]**
Every mature product separates four layers:
1. **Durable source-of-truth** (user notes, uploaded docs, authored curriculum) — small, rarely regenerated, backed up like any critical DB.
2. **Generated artifacts** (rendered cards, summaries, audio, exercise instances) — derived, reproducible, cheap to evict/regenerate, and generated **lazily / on first demand** wherever the product has full control over authoring (Anki, Quizlet, NotebookLM, ChatGPT), or **precomputed once centrally and reused across all users** where the content is not user-specific (Duolingo's exercise bank).
3. **Caches** (embeddings, media, rendered audio, prompt-prefix caches) — explicitly regenerable, TTL'd or invalidated on source change, and never treated as authoritative.
4. **Adaptive/scheduling state** (SM-2/FSRS factors, mastery scores, half-life regression parameters) — tiny per-item state, updated continuously and incrementally, stored separately from both content and cache because it must survive content regeneration and changes at a completely different (much higher) write frequency.

**Key inference relevant to M5.1:** none of the benchmarked products *eagerly generate full LLM content for every possible user/item combination up front*. Duolingo gets away with zero-marginal-cost scale because its exercise bank is centrally authored once and reused; NotebookLM/ChatGPT/Quizlet's AI features generate per-request and cache the result keyed by (source, request). This strongly favors a **lazy-generate + cache + separately-tracked adaptive state** design over full eager generation for any product with open-ended, user-specific content (which an AI study-plan/flashcard generator is).

## 2. Cost model: eager vs. lazy vs. continuous vs. hybrid at 1M users

### 2.1 Assumptions (explicit — change these to match real usage)

- **Users:** 1,000,000 monthly active.
- **Study items per user:** 200 flashcards/tasks generated per user's active study plan (a reasonable size for a multi-week plan). Eager designs generate all 200 up front for every user; lazy designs generate only what's actually studied.
- **Actual engagement:** 20% of generated items are ever studied (industry-typical long-tail drop-off for generated content) — i.e., lazy designs do ~1/5 the generation work of eager designs for the same population.
- **LLM generation cost per item:** ~800 input + 300 output tokens per flashcard/task (prompt with context + rubric). Using a mid-tier model at **$0.15/M input, $0.60/M output** tokens (roughly GPT-4o-mini-class pricing, 2024–2025 public list prices) → cost/item ≈ (800×0.15 + 300×0.60)/1,000,000 = **$0.00030/item**.
- **Storage:** generated item ≈ 1.5 KB text (JSON w/ metadata). Adaptive state (FSRS-style) ≈ 150 bytes/item. Embeddings for RAG grounding (if used) ≈ 1536 dims × 4 bytes = 6 KB/item if stored, or 3 KB if quantized (int8).
- **Storage pricing:** Postgres-class managed storage ≈ $0.10–0.25/GB-month (Supabase/RDS order of magnitude); object storage (S3-class) ≈ $0.023/GB-month; vector DB managed pricing ≈ $0.08–0.30/GB-month depending on provider — we use $0.15/GB-month blended.
- **Continuous/background regeneration:** re-generates or refreshes X% of items per month even if unread, to keep content "fresh" (e.g., spaced-repetition re-explanation, updated curriculum). Modeled at 10%/month of the full corpus.
- **Compute/orchestration overhead:** function invocations (edge functions / Supabase functions) at ~$0.20 per 1M invocations + ~$0.0000166/GB-s duration — treated as a small (<5%) adder and folded into a 15% operational overhead line rather than itemized per architecture, since it scales similarly across all four designs.
- **Maintenance labor** is modeled as engineering time (not cloud spend) and is the same order of magnitude across designs but shifts *where* effort goes (see §2.6).

All numbers below are **order-of-magnitude estimates for planning**, not vendor quotes.

### 2.2 Generation (inference) cost per month

| Design | Items generated/month | Formula | Monthly LLM cost |
|---|---|---|---|
| **Eager** (generate all 200 items for every user up front, once at plan creation; assume 1/12 of users create/regenerate a plan per month → steady-state ~83k plans/mo × 200 items) | 16.6M items/mo | 16.6M × $0.00030 | **≈ $5,000/mo** |
| **Lazy** (generate on first study touch; only 20% of items ever touched, spread over the plan's life; steady-state ≈ 3.3M items/mo) | 3.3M items/mo | 3.3M × $0.00030 | **≈ $1,000/mo** |
| **Continuous** (eager generation *plus* 10%/month background refresh of the full standing corpus of ~200M items [1M users × 200 items], to keep content current) | 16.6M (new) + 20M (refresh) ≈ 36.6M | 36.6M × $0.00030 | **≈ $11,000/mo** |
| **Hybrid** (lazy generation for first touch + light continuous refresh of only the "active" studied subset, ~20% of corpus, at 10%/month) | 3.3M (new lazy) + 4M (refresh of active subset) ≈ 7.3M | 7.3M × $0.00030 | **≈ $2,200/mo** |

**Takeaway:** Lazy cuts eager's inference bill by ~5x (matching the 20% engagement assumption almost exactly, as expected). Continuous is the most expensive because it pays full eager cost *plus* an ongoing refresh tax on content nobody may ever read. Hybrid captures most of lazy's savings while still keeping actively-used content fresh.

### 2.3 Storage cost per month (steady state, standing corpus)

Assume standing corpus after 12 months = 1M users × 200 items = 200M item-slots *possible*; actual stored rows differ by design:

| Design | Items actually stored | Item storage (1.5KB) | Adaptive state (150B, only for touched items) | Vector/embedding cache (optional, 3KB, only if RAG-grounded) | Total storage/mo (at $0.15/GB-mo blended) |
|---|---|---|---|---|---|
| Eager | 200M (all generated & stored) | 300 GB | 40M touched × 150B = 6 GB | 200M × 3KB = 600 GB (if embedded) | ~1,106 GB × $0.15 ≈ **$166/mo** |
| Lazy | 40M (only touched items persisted; untouched items never materialized) | 60 GB | 6 GB | 40M × 3KB = 120 GB | ~186 GB × $0.15 ≈ **$28/mo** |
| Continuous | 200M + monthly refreshed duplicates retained for rollback (assume 1 extra generation/version kept for 10% of corpus/mo, amortized +20M rows/mo → converges to ~240M steady) | 360 GB | 6 GB | 720 GB | ~1,086 GB × $0.15 ≈ **$163/mo**, but growing unboundedly without TTL/versioning discipline |
| Hybrid | 40M base + small refreshed-version overhead (~8M/mo versions, TTL'd to last 2 versions) | 72 GB | 6 GB | 144 GB | ~222 GB × $0.15 ≈ **$33/mo** |

**Takeaway:** Storage itself is cheap in absolute terms at this scale (all designs land in the tens-to-low-hundreds of $/month) — **storage is not the dominant cost driver; inference is.** But eager/continuous storage grows linearly and unboundedly with user count regardless of engagement, whereas lazy/hybrid storage tracks *actual usage*, which is the more defensible cost curve as the product scales past 1M users.

### 2.4 Combined order-of-magnitude monthly cost (inference + storage + 15% ops overhead)

| Design | Inference | Storage | +15% ops overhead | **Total/mo** | Annualized |
|---|---|---|---|---|---|
| Eager | $5,000 | $166 | ~$775 | **≈ $5,940** | ≈ $71k/yr |
| Lazy | $1,000 | $28 | ~$154 | **≈ $1,180** | ≈ $14k/yr |
| Continuous | $11,000 | $163 | ~$1,674 | **≈ $12,840** | ≈ $154k/yr |
| Hybrid | $2,200 | $33 | ~$335 | **≈ $2,570** | ≈ $31k/yr |

At 1M users, **eager costs ~5x lazy, and continuous costs ~10x lazy**, for the same nominal feature set. Hybrid lands at ~2x lazy but buys freshness guarantees eager/continuous partially provide — this is usually the right trade for a product that must avoid stale AI content complaints while still controlling burn.

### 2.5 Sensitivity — what could flip the conclusion

- If **engagement rises above ~60–70%** of generated items (users actually study almost everything generated), eager and lazy converge in cost, and eager's simplicity (predictable batch jobs, easier caching, no request-time latency) may win.
- If the **model cost drops 10x** (smaller/distilled models, on-device generation, or heavy prompt caching of shared curriculum context), inference stops dominating and storage/ops become comparable — favors doing more eager pre-generation since the penalty for waste shrinks.
- If **latency SLOs require instant item availability** (no visible "generating…" spinner ever), a hybrid design with **pre-warming for the *next N* items only** (a sliding window, not the whole plan) captures most of lazy's savings while hiding generation latency — this is the recommended middle path (see below).
- **Continuous/background refresh** cost is highly sensitive to the refresh rate assumption (10%/mo here); if curriculum content is largely stable, dropping refresh to 1–2%/mo (event-triggered only, e.g., source doc changed) collapses continuous's cost close to eager's.

### 2.6 Operational & maintenance cost differences (qualitative, same order of magnitude in $, different in engineering effort)

| Concern | Eager | Lazy | Continuous | Hybrid |
|---|---|---|---|---|
| Predictability of spend | High (batch, forecastable) | Lower (spend follows usage spikes) | Highest absolute, but predictable | Moderate |
| Latency exposure to user | None (pre-generated) | Visible on first touch unless pre-fetched | None | Minimal, with sliding-window pre-fetch |
| Failure blast radius | A generation-pipeline bug can corrupt/waste an entire cohort's content before anyone notices | Failures surface immediately per-user, easier to detect/rollback | Same as eager, amplified by repeated refresh runs | Bounded to active window |
| Data staleness / drift management | Requires an explicit invalidation strategy or content silently rots | Naturally fresh (generated against current context each time) | Explicit freshness by design, at highest cost | Freshness limited to what's actually used — good cost/freshness balance |
| Versioning & rollback complexity | Need to version 100% of a huge corpus | Only need to version the touched subset | Highest — versions everything, repeatedly | Only version the active subset |
| On-call/incident surface | Large nightly/batch jobs are a classic on-call pain point (cost-overrun runbooks like this repo's `docs/runbooks/cost-overrun.md` exist for exactly this reason) | Smaller, more frequent, easier-to-cap per-request jobs | Union of both eager's batch risk and lazy's per-request risk | Smallest combined surface |

## 3. Architectural recommendations for M5.1

1. **Adopt hybrid generation as the default:** generate items lazily on first study touch, but pre-fetch/pre-generate only the *next N items* (e.g., next 5–10) in a sliding window so the UI never blocks — this captures ~most of lazy's cost savings while eliminating visible generation latency.
2. **Separate the four layers explicitly in schema/storage, mirroring the benchmarked products:**
   - *Source of truth*: user inputs, uploaded material, plan parameters — never overwritten by generation, backed up like core account data.
   - *Generated artifacts* (flashcards/tasks/explanations): tagged with a `generation_version` and `source_hash` so they can be safely evicted/regenerated when source content changes, exactly as NotebookLM/ChatGPT treat derived summaries as regenerable, not authoritative.
   - *Caches* (embeddings, rendered content, prompt-prefix caches): TTL'd, never the only copy of anything important, and use provider-level **prompt caching** for repeated system/curriculum context to cut input-token cost on every lazy generation call.
   - *Adaptive/scheduling state* (mastery/interval/ease factors): a small, high-write-frequency table decoupled from item content, following the Anki/Duolingo/Quizlet pattern — this lets you regenerate or edit item content without disturbing a user's learning progress.
3. **Cap continuous refresh to event-triggered invalidation** (source doc edited, curriculum version bump, or explicit user "regenerate") rather than blanket time-based refresh of the whole corpus — this keeps freshness where it matters (Duolingo/NotebookLM pattern) without paying the ~10x continuous-refresh tax modeled above.
4. **Instrument spend against the two levers that actually move cost** (per §2.2/2.4): items-generated-per-month and refresh-rate-of-standing-corpus. Track both as first-class metrics/alerts (extending this repo's existing `docs/runbooks/cost-overrun.md`), since storage cost is a rounding error next to inference cost at this scale.
5. **Reuse Duolingo's zero-marginal-cost trick where content is not truly user-specific:** if a meaningful fraction of generated flashcards/tasks end up equivalent across users studying the same source material or curriculum topic, deduplicate/share generated items keyed by content hash before falling back to fresh per-user generation — this can push the effective "lazy" cost well below the modeled $1,000–$2,200/mo range.
6. **Re-run this model with real telemetry after 60–90 days** of production usage (actual engagement %, actual token counts, actual regeneration triggers) — the 20%-engagement and 10%-refresh assumptions above are the two inputs most likely to be wrong and most sensitive to the conclusion, per §2.5.
